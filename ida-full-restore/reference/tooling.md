# Инструменты: ida-multi-mcp, py_eval, сохранение

Ловушки ida-multi-mcp и IDA Python: предел 15 секунд, обрезка вывода, запреты py_eval, мелочи типового API, кэш декомпилятора, несколько баз сразу, сохранение и резервные копии. Часть навыка ida-full-restore; главное и оглавление — в SKILL.md.

## Никогда не вешай IDA длинным циклом внутри py_eval

**Это обязательное правило работы, а не совет по удобству.**

Выгрузка псевдокода всего модуля одним вызовом `py_eval` — самая частая причина того, что
экземпляр IDA перестаёт отвечать на час и больше. Клиент MCP при этом отваливается по
таймауту, **а цикл внутри IDA продолжает крутиться**: его нельзя ни остановить, ни
дождаться, ни обойти. Всё остальное — правки типов, переименования, замеры — встаёт в
очередь за ним.

На модуле в полторы тысячи функций такая выгрузка идёт около часа, на пятитысячном — дольше.
Час простоя ради одного числа в отчёте — цена, которую платить нельзя.

**Как надо: выгрузка по частям, каждый вызов возвращается сам.**

```python
# вызов N: отдать ровно CHUNK функций начиная с OFFSET и ВЕРНУТЬСЯ
import idautils, idc, ida_hexrays, ida_fpro
OFFSET, CHUNK = 0, 120
eas = list(idautils.Functions())[OFFSET:OFFSET + CHUNK]
qf = ida_fpro.qfile_t()
qf.open(r"...\dump_%06d.c" % OFFSET, "wb")
for ea in eas:
    qf.puts("// %s @ 0x%x
" % (idc.get_func_name(ea), ea))
    try:
        qf.puts(str(ida_hexrays.decompile(ea)) + "

")
    except Exception:
        qf.puts("// DECOMPILE FAILED

")
qf.close()
print(OFFSET + len(eas), "of", len(list(idautils.Functions())))
```

Куски потом склеиваются одной командой оболочки. Размер куска подбирается так, чтобы вызов
укладывался в отведённое время: 100–150 функций обычно безопасно, но у модуля с
гигантскими телами (одна функция на тринадцать тысяч строк псевдокода разбирается минутами)
кусок надо уменьшать до 20–40.

**Ещё три правила того же рода:**

1. **Любой проход по всем функциям разбивай на куски** — не только выгрузку. Замер следов,
   перепись комментариев, массовая смена типов: всё, что идёт по `idautils.Functions()`
   целиком, должно уметь начинаться с заданного места.
2. **Сначала правки, потом выгрузка.** Выгрузка — это измерение, а не работа. Снимать её
   надо ОДИН раз, после всех правок захода. Выгрузка до правок почти всегда выбрасывается.
3. **Если IDA всё-таки повисла, её можно поднять.** База при жёстком завершении не теряется:
   распакованные `.id0/.id1/.id2/.nam/.til` рядом с `.i64` содержат рабочее состояние, и
   IDA, запущенная с ключом `-A` (он сам отвечает на вопрос о неаккуратном закрытии),
   продолжает с них. Проверено: пережили и переименования, и правки типов. Но описания,
   поставленные ПОСЛЕ последнего сохранения, терялись, поэтому
   **`idb_save` после каждой пачки правок** — и держи на диске TSV с тем, что применял,
   чтобы повторить одним вызовом.

## Работай только аналитически, без пакетной обработки

Это жёсткое требование, а не пожелание.

- **По одной функции за раз.** Прочитал тело — понял — назвал — прокомментировал
  — перепроверил декомпиляцию. Потом следующая.
- **Имя и комментарий появляются только после чтения тела.** Шаблонная
  простановка имён по образцу («у всех типов слот +0x28 это ReadBody, значит
  подпишем все скопом») разбором **не считается**.
- Массовое применение допустимо только для **механического следствия уже
  проверенного факта** — например, разложить таблицу указателей по адресам.
  Но смысл каждой записи всё равно проверяется отдельно.
- Если сделал что-то пакетно — скажи прямо и отдельно перечисли, что не
  прочитано вручную.
- **Осторожно с массовыми правками комментариев.** Скрипт «оставить один из
  двух комментариев» легко сносит собственный разбор. Перед удалением смотри,
  что удаляешь, и держи свежий экспорт `decompile_to_file` — заголовочный блок
  `//` в нём и есть комментарий функции, из него всё восстанавливается.

**Поиск имени переменной в тексте псевдокода делается только по границам
слова.** Обычный `in` ловит `insna` в поиске `insn` — и массовая правка,
построенная на таком поиске, портит именно те функции, которые были в порядке.
У меня так ушло 16 обработчиков кодов операции: у каждого есть местный буфер
`insna`, приведение `(AVSBX_MODRM *)insna` совпало с подстрокой
`(AVSBX_MODRM *)insn`, и правильный довод `AVSBX_INSN *insn` был подменён на
`AVSBX_MODRM *op`. Пришлось откатывать.

Проверка границы занимает три строки и ставится один раз:

```python
def tok(line, name):
    i = line.find(name)
    while i >= 0:
        a = line[i-1] if i else " "
        b = line[i+len(name)] if i+len(name) < len(line) else " "
        if not (a.isalnum() or a == "_") and not (b.isalnum() or b == "_"):
            return True
        i = line.find(name, i + 1)
    return False
```

И второе правило к той же истории: **перед массовой правкой выпиши список
адресов, которые трогать нельзя.** Для обработчиков кодов операции такой список
собирается из самих таблиц за десяток строк, и тогда ошибочная правка просто не
доходит до них.

## Работа через ida-multi-mcp: что надо знать заранее

Инструмент удобный, но у него десяток мест, где он молчит вместо ошибки или
ведёт себя не так, как подсказывает имя. Всё перечисленное проверено на
практике; каждая строка здесь стоила отдельного круга проб.

### Имена доводов у инструментов не угадываются

`decompile` хочет `addr`, а не `address`. `find_bytes` хочет `patterns`
(**массив**), а не `pattern`. `declare_type` хочет `decls`, а не
`c_declaration`. `enum_upsert` хочет `queries`. Ошибка при этом вежливая и
называет недостающий довод — **читай её, а не угадывай второй раз**.

### `declare_type` режет объявление по запятым

Объявление перечисления с несколькими членами через `declare_type`
**разваливается**: инструмент дробит текст по запятым и пытается разобрать
каждый кусок отдельно, получая «Syntax error near» на каждом члене.

Любые объявления с запятыми (перечисления, структуры с несколькими полями,
прототипы с несколькими доводами) заводятся через `py_eval`:

```python
n = idc.parse_decls(decl, ida_typeinf.PT_REPLACE)   # 0 ошибок — значит принято
```

`PT_REPLACE` обязателен, если тип уже есть: иначе объявление молча не
применится. Текст объявления удобно писать файлом и читать его из `py_eval`
через `ida_fpro.qfile_t` — тогда не упираешься в длину строки.

### `decompile_to_file` без `mode="merged"` портит рабочий каталог

По умолчанию он пишет **по файлу на функцию**, а на именах, где есть знаки,
недопустимые в именах файлов Windows (`?` из украшенных имён C++), падает с
`Internal Error: OSError` — уже после того, как разложил по каталогу сотни
файлов. Выглядит как полный отказ, на деле частичный результат уже на диске и
мешается.

Правила:

- всегда `mode="merged"` — один файл;
- каталог перед выгрузкой создавать пустым;
- `all=true` обязателен, иначе инструмент требует `addrs`;
- на большой базе выгрузка идёт минутами и уезжает в фоновую задачу; **база всё
  это время занята**, и другие вызовы к ней встанут в очередь.

Если `mode="merged"` почему-то недоступен, выгрузку надёжнее сделать самому
из `py_eval` кусками по 200–300 функций, дописывая в один файл:

```python
f = ida_fpro.qfile_t(); f.open(path, 'at')
for ea in sorted(idautils.Functions())[LO:HI]:
    f.puts('// %s @ 0x%x\n' % (ida_funcs.get_func_name(ea), ea))
    for ln in (idc.get_func_cmt(ea, 1) or '').split('\n'):
        if ln.strip(): f.puts('// ' + ln + '\n')
    cf = ida_hexrays.decompile(ea)
    f.puts((str(cf) if cf else '// ОШИБКА') + '\n\n')
f.close()
```

Заголовочная строка с именем и адресом нужна обязательно: по ней потом
считается мерка и находятся функции в тексте.

### Заголовки в выгрузке берутся из кэша сервера, а тело — из декомпилятора

Неприятная мелочь, на которой легко потерять час. Строка-заголовок, которую
`decompile_to_file` пишет перед каждой функцией, берётся из **индекса сервера**,
а не из базы. Если переименовать функции и сразу выгрузить, в заголовках будут
СТАРЫЕ имена, а в самом псевдокоде — новые:

```
// AvAlgol_GvmSem64_182 @ 0x163904e50      <- старое имя, из кэша
char __fastcall AvAlgol_Sem_Cpuid(AVALGOL_GVM *gvm)   <- новое, от декомпилятора
```

Комментарии к функции при этом тоже свежие. Практический вывод: **искать в
выгрузке надо по адресу, а не по имени**, и не пугаться, когда `grep` по новому
имени не находит заголовка. Переименование заголовков делается потом, по карте
«адрес → имя», снятой из базы отдельно.

### Предел 15 секунд на вызов — это предел на ЦИКЛ, а не на операцию

Один `decompile` крупной функции в предел укладывается, а цикл по тысяче
функций — нет, и обрывается посередине с `Tool timed out after 15.00s`. При
этом **часть работы уже сделана**: если цикл писал в файл, файл обрезан на
середине последней функции, и его надо обрезать до последнего целого заголовка
и продолжить с нужного индекса.

Ориентиры: декомпиляция — 200–300 функций за вызов; дешёвый обход команд
(`get_operand_type`) — несколько тысяч; простые переименования — тысячи.
Счёт всегда вести по индексу в `sorted(idautils.Functions())`, чтобы
продолжение было воспроизводимым.

### Результат `py_eval` обрезается при показе

Длинная строка возврата приходит усечённой с пометкой вида `[13814 chars
total]`. Это **показ**, а не ошибка: данные были. Всё, что длиннее пары
десятков строк, надо писать в файл (`ida_fpro.qfile_t.puts`) и читать снаружи
обычными средствами, а в возврат класть только сводку.

### Постоянный шум в stderr — не ошибка

На каждый вызов `py_eval` приходит:

```
[py_eval] IDA module 'ida_struct' could not be imported...
[py_eval] IDA module 'ida_enum' could not be imported...
```

В IDA 9.x этих модулей нет вовсе, работать надо через `ida_typeinf`. Сообщение
печатается всегда и ни на что не влияет — не принимай его за отказ.

### Исключение внутри `py_eval` приходит полным следом вызовов

Это самое полезное свойство инструмента: в `stderr` лежит обычный traceback с
номером строки твоего же кода. Читай его целиком, а не только последнюю строку —
там видно, какой именно вызов IDA отказал.

Две ошибки, которые ловятся так каждый раз:

- `TypeError: '<' not supported between instances of 'str' and 'NoneType'` —
  `ida_funcs.get_func_name` вернул `None` (адрес не начало функции), и это
  попало в `sorted`. Лечится `or '?'`;
- `missing 1 required positional argument` — у функции IDA другой порядок
  доводов, чем кажется (см. ниже про `restore_user_lvar_settings`).

### Возвраты у типового API несовместимы между собой

Самая дорогая ловушка: **`set_named_type` и `set_type_cmt` возвращают 0 при
УСПЕХЕ** — это код ошибки, а не признак. `idc.SetType`, наоборот, возвращает
`True`/`False`. Если проверять «истинность» возврата одинаково, половина правок
будет выглядеть несделанной, а половина несделанных — сделанной.

Проверять надо не возврат, а результат: перечитать тип и сверить размер.

```python
ok = t.set_named_type(til, 'NAME', ida_typeinf.NTF_REPLACE)   # 0 — успех
t2 = ida_typeinf.tinfo_t(); t2.get_named_type(til, 'NAME')
assert t2.get_size() == ожидаемый
```

### Мелочи типового и декомпиляторного API, на которых спотыкаешься

- `udm_t.offset` и `udm_t.size` — **в битах**, не в байтах;
- `udt_type_data_t` не имеет `.pop()` и вообще плохо правится на месте:
  собирай новый, перенеся `taudt_bits`, `sda`, `pack`, `effalign`;
- `lv.type` у локальной переменной — **связанный метод**, а не свойство:
  `str(lv.type())`. Сравнение `str(lv.type)` молча не совпадёт ни с чем;
- `restore_user_lvar_settings(lsi, ea)` принимает вектор **первым** доводом;
- `lvar_saved_info_t` без заполненного `.ll`
  (`lvar_locator_t(lv.location, lv.defea)`) — тихая пустышка;
- `tinfo_t.create_ptr(ptr_type_data_t)` со взведённым `TAPTR_SHIFTED`
  возвращает `False` и оставляет пустой тип; сдвинутый указатель заводится
  только через `parse_decls`;
- `get_tid()` у typedef — `-1`; нужен тип с собственным именем, а библиотечный
  сперва втянуть `idc.import_type(-1, "_CONTEXT")`;
- после любой правки типов — `ida_hexrays.clear_cached_cfuncs()`, иначе
  псевдокод отдаётся старый;
- у свежего `cfunc` `treeitems` пуст, пока не вызван `get_pseudocode()`.

### Удаление типа оставляет подвисшие ссылки в сохранённых локалях

`del_named_type` не проверяет, кто на тип ссылался. Сохранённый тип локальной
переменной превращается в `struct #89 *`, и функция начинает печататься как до
разбора — а выглядит это как внезапно испортившаяся декомпиляция.

Поэтому после каждого удаления или переименования типа — проход по базе:

```python
for ea in idautils.Functions():
    lsi = ida_hexrays.lvar_uservec_t()
    if not ida_hexrays.restore_user_lvar_settings(lsi, ea): continue
    for lv in lsi.lvvec:
        if '#' in str(lv.type):   # подвисшая ссылка
            ...
```

### Висячий ординал типа — след машины, которого не видит НИ ОДНА мерка

Обратная сторона предыдущего раздела: тип удалили когда-то давно, а ссылки на
него остались, и база досталась уже в таком виде. Hex-Rays печатает такую
переменную как `#164 *p`, и дальше всё обращение к ней вырождается в слепую
индексацию: `*((_DWORD *)p + 19)`, `*((_QWORD *)p + 10)`.

Опасность в том, что **все мерки готовности на такой функции молчат**: имя у
переменной есть, тип формально есть, прототип есть, описание есть. В aeheur так
прожили 24 указателя на общий слот ядра в шести функциях плюс поле структуры, и
нашлись они окольным путём — через номерное имя функции
`AvHeur_GetParentCtx_Field_0040`, у которой номер был не свой, а взят из имени
поля, которое она читает.

Проверка дешёвая и должна идти в общий список наравне с остальными:

```
grep -oE "#[0-9]+ \*?" выгрузка.c | sort | uniq -c | sort -rn
```

Ноль тут достижим. Опознаётся настоящий тип по тем же правилам, что и всё
остальное: совпадение смещений и ширин с уже доказанной записью. У слота (7,3)
совпало шесть мест, из них два — с указателями на именованные структуры, и этого
достаточно.

Отдельно: **один объект может быть описан в базе дважды**. Там же нашлась вторая
запись того же размера на тот же слот, с полями, которых никто не читает и не
пишет, и противоречащими доказанным. Признак — запись используется в одном месте
и только ради одного поля. Такую надо удалять, а не «оставить на всякий случай»:
она утверждает неправду о раскладке.

### Пакетные правки делаются из `py_eval`, а не отдельными вызовами

У сервера есть `rename`, `set_type`, `set_comments` и прочие удобные
инструменты, но каждый из них — отдельный круг обращения. Там, где правок
больше трёх, дешевле один `py_eval` со списком: он и быстрее, и даёт общий
протокол в возврате («ok / ERR» по каждой записи), по которому сразу видно,
что не применилось.

И отдельно: **`rename` умеет молча не сработать**. Переименовывать надёжнее
`idc.set_name(ea, name, idc.SN_NOWARN)`, а адрес брать у
`ida_funcs.get_func(ea).start_ea`, а не у места, на которое смотришь.

### Несколько баз — это нормально и это главный способ не ждать

Одна база занята длинной операцией — работай с другой: вызовы к разным
`instance_id` идут параллельно. Выгрузка на 14 тысяч функций занимает минуты,
и за это время можно успеть разобрать соседний модуль или поработать с файлами
на диске.

`list_instances` показывает `pid`. Если вызов отвечает
`Failed to connect to instance: ConnectionRefusedError`, процесса **уже нет** —
проверяется `tasklist` по этому `pid`. Тогда распакованный набор
(`.id0 .id1 .id2 .nam .til`) остался от падения: его отводят в сторону и
поднимают `.i64` заново, **в том числе самому**:

```
nohup "/c/Program Files/IDA Professional 9.2/ida.exe" база.i64 >/dev/null 2>&1 &
```

`.id1` появляется секунд за десять. После подъёма `instance_id` **всегда
новый**; старый висит в списке мёртвой записью.

`Tool timed out` — другое: окно живо, база занята. Лечится дроблением работы,
а не перезапуском, — **но только пока видно продвижение**.

Самый надёжный признак «считает, а не зависла» — прирост ПРОЦЕССОРНОГО времени
процесса. Окно отвечает (`Responding=True`) и при зависании, файл-отметка растёт
не всегда, а счётчик CPU не врёт:

```powershell
$p = Get-Process -Id <pid>; $t1 = $p.TotalProcessorTime; Start-Sleep 6
$p.Refresh(); ($p.TotalProcessorTime - $t1).TotalSeconds
```

Около 6 с за 6 с — занято одно ядро, идёт работа, надо ждать. Около нуля при
незакрытом вызове — это зависание, и тогда перезапускать.

**И главное: не создавай себе такой работы.** Массовая правка локалей, написанная
через полный обход базы с декомпиляцией КАЖДОЙ функции, занимает главный поток на
десятки минут и блокирует всё остальное; отменить её со стороны MCP нельзя —
отменяется только ожидание, а цикл внутри иды живёт дальше. Список функций,
которые надо тронуть, почти всегда дешевле получить из ВЫГРУЗКИ (`grep` по
псевдокоду), а в базу идти уже по готовому списку. Признак живости
один: файл-отметка текущего куска растёт или появился следующий
`doneNNNNNN.txt`. Если за два подряд вызова отметка не сдвинулась — база
зависла, и её надо поднимать заново, а не пережидать. Указание пользователя на
этот счёт прямое и повторённое: **зависшую иду перезапускать.**

И про размер куска. Предел у MCP — 120 секунд на вызов, а цикл внутри иды живёт
дальше. Если кусок настолько велик, что вызов не возвращается, работа не
теряется, но пропадает возможность отличить «считает» от «зависла» по возврату.
Поэтому бюджет куска подбирают так, чтобы вызов обычно укладывался в предел; на
больших порождённых функциях правил это сотни килобайт, а не мегабайты.

### `analysis_status` — снимок, а не защёлка

`finished: true` означает «в эту секунду очередь пуста», а не «анализ
закончен»: IDA доставляет работу заново. Durable-признак — `function_count`,
переставший меняться между вызовами.

## Сохранение, зависания и ограничения инструментов

Это не бытовые мелочи: на них теряется больше времени, чем на самом разборе.

### Сохраняйся часто

- Переименования, типы и комментарии живут **только в памяти**, пока не вызван
  `idb_save`. Падение IDA до сохранения — потеря всей работы за проход.
- Сохраняй после каждого осмысленного шага: разобрал функцию — сохранил.
  Не «в конце», а по ходу.
- **Обязательно сохраняйся ПЕРЕД рискованным**: правкой полей структуры,
  массовой правкой комментариев, экспериментом с типами. Тогда откат стоит
  перезапуска, а не дня работы.
- Сохранять надо **каждую** базу, с которой работал, по её `instance_id`, —
  чужую тоже.
- **Держи рядом ОДИН бэкап и перезаписывай его**, а не копи пронумерованные: база
  крупного модуля весит полгигабайта. Копировать только ПОСЛЕ того, как `idb_save`
  отчитался: на крупной базе сохранение уходит в фон, и до его конца файл на диске
  неполон. Момент перезаписи виден по времени изменения файла, а копию стоит
  сверить:

```bash
cp -f aeheur.dll.i64 aeheur.dll.i64.bak && cmp -s aeheur.dll.i64 aeheur.dll.i64.bak
```

### Кеш декомпилятора после тайм-аута

Разбиение работы на куски и перезапуск базы описаны выше, в разделе про
ida-multi-mcp. Здесь — то, что относится к самому декомпилятору:

- после тайм-аута кеш может остаться битым: `treeitems` пуст, хотя `str(cf)`
  выдаёт текст. Лечится `clear_cached_cfuncs()` и повторной декомпиляцией;
- не держи несколько объектов `cfunc` одновременно: новая декомпиляция
  обесценивает предыдущий, и его `treeitems` молча становится пустым. Это
  выглядит как «функция без вызовов» и уводит в ложные выводы.

### Массовая правка прототипов теряет список параметров

Приём «взять нынешний тип функции, подменить только возврат и записать обратно»
выглядит безопасным, но у части функций возвращается тип **без параметров**, и
после записи функция остаётся с пустым списком. Псевдокод тогда разваливается:
доводы превращаются в сырые обращения к регистрам, а все точки вызова печатаются
как `f()`.

Проверять надо сразу после правки — перепись по базе:

```python
[f for f in idautils.Functions() if "__fastcall()" in (idc.get_type(f) or "")]
```

Если список не пуст, прототипы берутся из **прошлой выгрузки** `decompile_to_file`:
там сигнатура напечатана целиком, и восстановить её точнее, чем угадывать по
телу. Поэтому старые выгрузки не надо удалять, пока проход не закончен.

### Чего нельзя в py_eval

Проверено на практике, чтобы не выяснять заново:

- импортируются **только** модули IDA (`ida_*`, `idaapi`, `idautils`, `idc`);
  `re`, `struct`, `collections`, `json`, `sys`, `os` — нельзя;
- нет `open`, `exec`, `dir`, нельзя объявлять классы;
- глобальные переменные **не переживают** вызов: вспомогательный код
  приходится присылать заново каждый раз либо переносить расчёт наружу;
- файлы пишутся через `ida_fpro.qfile_t` (`puts` работает, `write` — нет),
  читаются через `read` — но **`read` на двоичных данных падает**
  `UnicodeDecodeError`: байты надо сперва вывести в текст (шестнадцатеричный
  дамп) и читать уже его.

Отсюда общее правило: **тяжёлое считать снаружи**. Выгрузил псевдокод
`decompile_to_file` — и меряй, ищи и классифицируй обычным Python, а в IDA
возвращайся только за правками.

### Имена в заголовках выгрузки устаревают массово, и это ломает разбор по окружению

Правило «заголовок берётся из индекса сервера, а тело от декомпилятора» известно,
но масштаб обычно недооценивают. На `aealgol` после одного захода работы
**3 571 заголовок из 13 794 оказался с устаревшим именем** — четверть файла.

Для счёта следов это неважно (считаются тела), а вот любой разбор по именам —
окружение, семьи, долг в именах — на такой выгрузке врёт. Проверка показывала
970 функций с приставкой `AvAlgol_DetectFormat_`, когда в базе их оставалось 726.

Лечится дёшево, без новой выгрузки: снять из базы карту «адрес → имя» и
переписать заголовки на месте.

```python
# в IDA
for ea in idautils.Functions():
    f.puts("%x\t%s\n" % (ea, idc.get_func_name(ea)))
```

```python
# вне IDA
HDR = re.compile(r'^// (\S+) @ (0x[0-9a-fA-F]+)$')
m = HDR.match(line)
if m:
    nm = names.get(int(m.group(2), 16))
    if nm: line = '// %s @ %s\n' % (nm, m.group(2))
```

Имена в ТЕЛАХ (точки вызова) так не поправятся — они из декомпилятора на момент
выгрузки. Поэтому после крупной порции переименований выгрузку всё-таки надо
обновить, но для разбора по спискам функций хватает и переписанных заголовков.

## Имена в выгрузке псевдокода отстают от базы — сопоставлять надо по адресу

Любой разбор, который идёт по выгрузке псевдокода, рано или поздно сводит её с чем-то, снятым
из базы: со списком функций, с комментариями, с прототипами. И здесь лежит ловушка, которая не
даёт ни ошибки, ни предупреждения.

**Имена функций в выгрузке — на момент её снятия, а иногда и старше.** После переименования
выгрузка продолжает печатать прежнее имя: и в заголовке функции, и в вызовах внутри чужих тел.
Сопоставление «по имени» поэтому молча теряет всё, что успели переименовать.

Проверено счётом: на aealgol из 5 523 целей имя совпало у 4 408, а **у 1 115 разошлось** —
каждая пятая. Примеры расхождений:

| В базе | В выгрузке |
|---|---|
| `AvAlgol_ClearLinkedNodeList` | `AvAlgol_FmtPdf_u5` |
| `AvAlgol_BxLog_IsEventEnabled` | `AvAlgol_DetectFormat_u2` |
| `AvAlgol_ScanRangeBySignatures` | `AvAlgol_DetectFormat_h2` |

Заметить это по итогу невозможно: инструмент отрабатывает, выдаёт меньше находок, чем мог бы,
и выглядит исправным. Обнаружилось случайно — при проверке, почему функции с явно знакомым
устройством не попали в выдачу.

**Правило.** В заголовке каждой функции выгрузка печатает адрес (`// имя @ 0x…`). Сводить
выгрузку с базой надо **по адресу**, а имя из выгрузки использовать только внутри самой
выгрузки — там оно согласовано: и заголовки, и вызовы в телах пользуются одним и тем же старым
именем.

```python
HDR = re.compile(r'^// (\S+) @ 0x([0-9A-Fa-f]+)\s*$')
# имя из выгрузки -> адрес; дальше всё, что приходит из базы, искать по адресу
```

**Проверка на одну команду, которую стоит делать перед каждым таким разбором:** посчитать, у
скольких целей имя из базы совпало с именем из выгрузки. Если совпало не у всех — сопоставление
по имени уже врёт, и насколько именно, видно сразу.
