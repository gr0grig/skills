# Восстановление собираемого исходного кода по базе IDA

Навык основан на двух портах проигрывателя Game Maker («Братья Пилоты», PILOTS.EXE
и PILOTS2.EXE): 11 тыс. строк C17, MSVC x86, игра запускается на современной Windows.

## Что значит «готово»

1. **Собирается** одной командой без предупреждений (`/W4 /WX`), в выпуске и в отладке.
2. **Работает**: программа запускается на реальных данных и проходит основные сценарии.
3. **Читается как исходник**, а не как выгрузка IDA (список следов — ниже).
4. **Повторяет оригинал**, включая его странности. Каждое сознательное отступление
   отмечено в коде и перечислено в README.
5. **Задокументировано**: README в корне, `docs/` по подсистемам, лицензия.

Не готово, пока хоть один пункт не проверен *запуском*, а не чтением кода.

## Предусловие

База должна быть разобрана навыком `ida-full-restore`: имена, прототипы, структуры
с проверенными размерами, перечисления, комментарии. Переписывать недоразобранную
функцию — значит закрепить в исходнике чужую догадку. Если при переписывании видно,
что имя или тип в базе врут, — сначала правь базу, потом исходник.

## Следы IDA, которых в исходнике быть не должно

Пользователь проверяет это и справедливо возмущается каждой находкой:

- комментарии регистров и кадра: `// ebx`, `// [esp+10h] [ebp-Ch]`, `BYREF`;
- имена `v1`, `a2`, `sub_`, `LABEL_12`, `goto` ради потока, который IDA не свернула;
- `LOBYTE/HIWORD/BYTE1`, `__PAIR64__`, `_DWORD`, `_BYTE`, `*(_DWORD *)(p + 8)`;
- `__usercall`, `@<eax>`, `__spoils`, `__fastcall` там, где это была особенность компилятора;
- `JUMPOUT`, `__asm`, `MEMORY[...]`;
- обратный порядок доводов (см. ниже) и приведения, которые были нужны только Hex-Rays.

Проверка — grep по всему дереву перед каждым отчётом. Отдельно смотри, не
скопировались ли в новый каталог *старые* файлы с этими следами.

## Порядок работы

### 1. Каркас

- Один общий заголовок (`gm.h`): все типы формата, глобальные, прототипы.
  Размер **каждой** структуры, которая читается из файла или лежит в памяти
  по фиксированной раскладке, — `_Static_assert(sizeof(T) == N)` по числу из базы.
  Если формат хранит 32-разрядные указатели — `_Static_assert(sizeof(void*) == 4)`
  и сборка только x86.
- `data.c` — определения глобальных с начальными значениями, снятыми с байтов базы
  (таблицы, строки, ключи). Имена — как в базе.
- Модули — по подсистемам, а не по адресам: окно/хост, такт, правила, объекты,
  машина скриптов, встроенные функции, загрузка, сохранения, вывод, звук, фильмы.
- `build.bat` с явными путями к MSVC и SDK, `/std:c17 /W4 /WX /utf-8`,
  выпуск и `debug`; ресурсы (`.rc` со значком, извлечённым из оригинального EXE).

### 2. Переписывание функций

Для каждой функции: псевдокод из базы → естественный C.

- **Порядок доводов.** Hex-Rays показывает доводы `__stdcall`/`pascal` в порядке
  стека. В исходнике — естественный порядок; переходники (таблицы вызовов из
  скриптов) снимают доводы со стека явно: `args[0]` — вершина. Ошибка здесь
  молча меняет местами числа — проверяй по местам вызова.
- **Скрытые доводы в регистрах.** Функция с `__usercall` может брать довод из
  регистра, который вызывающий вообще-то держит для другого (во второй части номер
  ресурса уходил в пакет графики как «предыдущий тип записи» через EDI). Такое
  воспроизводится явным доводом и комментарием «Особенность оригинала».
- **Ассемблерные части → стандартный C.** Свой `memcpy/strlen/...` — библиотечные
  вызовы; `setjmp/longjmp` — стандартные; машина скриптов, которая держала стек
  в стеке x86, — собственный массив (и сброс его при `longjmp`). Библиотеку C
  оригинала (Digital Mars, MSVC CRT) не переносить — пользоваться своей.
- **Копирование на месте.** Где оригинал разбирает поток и пишет результат поверх
  него же (свой `memcpy` копирует вперёд), в C нужен `memmove`.
- **Неопределённое поведение оригинала** (чтение неинициализированной переменной,
  регистра, мусора со стека) — не воспроизводить, а дать разумное значение и
  отметить: «Особенность оригинала: … ; здесь — …».
- **Странности без UB** (ошибки на единицу, неочищенные хвосты файлов, потерянный
  байт в сохранении) — воспроизводить как есть, с комментарием «Особенность
  оригинала». Пользователь может потом попросить исправить отдельные — тогда это
  отступление и строка в README.
- Комментарий функции — что она делает и зачем, без адресов и без пересказа
  ассемблера.

### 3. Данные игры/приложения

Если данные дописаны в хвост оригинального EXE, у пересобранного EXE их нет:
проверь хвост своего файла, и при отсутствии открой оригинальный EXE из того же
каталога. Отметь это в README. Имена производных файлов (сохранения, справка)
должны остаться такими же, как у оригинала, — иначе старые сохранения не найдутся.

### 4. Сборка

Собирай после каждого крупного модуля. `/WX` не отключать: предупреждения ловят
урезания и забытые доводы. Устаревшие API, без которых не обойтись (`GetVersion`
для различения NT/9x/Win32s), — `#pragma warning(suppress : 4996)` с объяснением.

### 5. Запуск и проверка

- **Перед первым запуском сделай копию пользовательских файлов** (сохранения,
  настройки) в рабочий каталог — программа их перепишет. После проверки сравни
  и при необходимости верни.
- Запускай из каталога оригинала (рядом с данными).
- Снимки окна: `PrintWindow(h, hdc, 3)` из PowerShell. Дочерние окна MCI (AVI)
  на снимке чёрные — это не ошибка вывода.
- Хэндл главного окна бери заново на каждом шаге: сначала может быть заставка.
- Щелчки по времени ненадёжны — жди состояния по пикселям (2–3 опорные точки
  с известными цветами), потом щёлкай.
- Сохранения сравнивай побайтно с файлами оригинала: размер и раскладка должны
  совпасть, различаться — только данные состояния.
- Если оригинал на этой системе не запускается — сверяй поведение по коду
  и скажи об этом прямо.
- Финальную проверку отдай пользователю: запусти EXE и перечисли, что проверить.

### 6. Отступления ради современной Windows

Найдены на практике; проверяй каждое в новом проекте:

- пути длиной 64–128 байт → `MAX_PATH` (оригинал падает в глубоком каталоге);
- размер окна считался вручную → `AdjustWindowRectEx` (иначе клиентская область меньше);
- `waveOutSetVolume` теперь задаёт громкость всего приложения (звуки глушат MIDI),
  `midiOutGetVolume` у синтезатора не работает (громкость музыки читается как 0) →
  программная громкость;
- щелчок, остановивший AVI, проходит отпусканием кнопки в окно под ним → проглотить
  следующий `WM_LBUTTONUP`.

Каждое — в README в разделе «Отличия от оригинала», с причиной.

### 7. Документация

- Корневой `README.md`: что это за программа (по `README.TXT` игры, а не по
  догадке), откуда восстановлено, сборка, запуск, отличия от оригинала, лицензия.
- `LICENSE` (MIT по просьбе) и оговорка: лицензия не распространяется на
  оригинальную программу и её данные.
- `docs/` — по странице на подсистему: архитектура и поток выполнения, вывод,
  скрипты (таблица встроенных функций с номерами), звук, ввод, формат файла,
  память, сохранения, видео, интерфейс. Документация описывает код, который
  есть, — после изменений кода её надо обновить, старые формулировки врут.

## Перенос порта на следующую версию программы

Когда есть разобранная база версии 1 с готовым портом и база версии 2 того же движка:

1. **Доведи базу версии 2 до уровня версии 1** (перенос разметки по совпадающим
   функциям) и проверь полноту переноса, а не только имена: типы членов кадра,
   типы локальных переменных, выбор членов объединений, пользовательские метки,
   типы и имена глобальных. Сравни выгрузки обеих баз и найди всё, что в версии 2
   хуже, чем в версии 1, — это пропуски переноса.
2. **Разница типов**: выгрузи все типы обеих баз и сравни текстом — так находятся
   изменённые структуры (размеры, новые поля), версии форматов, новые значения
   перечислений.
3. **Разница кода**: выгрузи псевдокод обеих баз *в одном формате* и сравни по
   именам функций с нормализацией (без комментариев и объявлений). Отсей шум от
   переименований и собственных правок типов; оставшееся — настоящие изменения.
   Список «пар» из сопоставителя быстро устаревает — сверяйся с текущими базами.
4. **Разница данных**: строки, таблицы (например, таблица встроенных функций —
   какие номера добавились).
5. **Скопируй проект версии 1** (проверь список файлов после копирования: копия
   по `git ls-files` из подкаталога теряет файлы) и перенеси каждое изменение:
   новые поля и константы в заголовок, изменённые функции, новые функции.
6. Обнови имена файлов, значок, имя собранного EXE.
7. Отступления версии 1 пересмотри: если версия 2 сама исправила то, что в
   версии 1 пришлось обходить (громкость), — повторяй оригинал версии 2, а не обход.
8. Напиши `docs/changes.md`: что изменилось в коде по сравнению с версией 1 —
   формат (таблица старое/новое), новые и изменённые функции списком, по подсистемам,
   и новые отступления. Ссылку на проект версии 1 давай так, как попросит
   пользователь (обычно на репозиторий).

## Ловушки окружения

- Правки многострочных фрагментов делай Python-скриптом в файле
  (`replace` с проверкой `count == 1`), а не heredoc с кавычками в Bash — оболочка
  ломается на кавычках. Сохраняй окончания строк файла (`newline=""`).
- `build.bat` запускай из PowerShell (`& путь\build.bat`): `cmd //c` из Git Bash
  его не находит. Строки `rem` в UTF-8 дают безвредный мусор в выводе cmd.
- Не трогай чужие базы IDA, открытые в соседних экземплярах.

## Отчёт

Коротко и честно: собирается ли (обе конфигурации), что проверено запуском и что —
только по коду, какие отступления добавлены, тронуты ли файлы пользователя и
возвращены ли, где лежит EXE. Не коммить без просьбы.
